01 / 05 — Overview

리드 소싱 파이프라인 전체 구조

고객사 단위로 실행되는 Airflow DAG 3개가 온보딩부터 데이터 서빙까지 수행합니다.

▾ 온보딩

  1. URL·자료 파싱 고객사가 제공한 정보 파싱
  2. 기업 정보 정형화 파싱된 정보 데이터 정형화
  3. 수출 타겟 ICP 추론 정형 데이터를 기반으로 한 LLM ICP 추론
  4. 소싱 필터 조건 생성 추론된 ICP를 기반으로 한 LLM 소싱 필터 생성

TriggerDagRunOperator

▾ 리드 발굴

  1. 필터 기반 1차 발굴 생성된 필터 기반 리드 1차 발굴
  2. 적합도 스코어링·판별 1차 발굴 기업에 대한 2차 LLM 적합 판별 퍼널
  3. 적합 기업 재직자 조회 적합 기업의 재직자 리스트 전체 조회
  4. 직무 기반 1인 선정 재직자 리스트 중 1순위 컨택 리드 LLM 판별
  5. 최종 리드 Enrichment 최종 리드 1인 데이터 수집

TriggerDagRunOperator

▾ 이메일 유효성 검증 및 데이터 서빙

  1. 이메일 유효성 검증 도메인 평판 관리를 위해 이메일 유효성 검증 진행
  2. S3 적재 및 포털 서빙 소싱된 리드 데이터 적재 및 데이터 포탈 서빙
  • DAG 간 TriggerDagRunOperator로 순차 진행

02 / 05 — Onboarding

LLM 온보딩 자동화: 7~10일 → 1일 이내

Problem

고객사가 ICP, 타겟, 기업 소개, 강점, 차별점, 영업 전략 등을 직접 입력해야 했습니다. 다량의 항목이고, 어떤 정보를 입력해야 할지 몰라 온보딩 단계에서 병목이 생기고, GTM 팀의 문의 대응에 리소스 소모가 컸습니다.

Logic
  1. 웹페이지는 Crawl4AI + LLM, 세일즈 자료는 OCR 파이썬 라이브러리 + LLM으로 파싱
  2. LLM으로 파싱된 데이터를 정형 스키마(소개, 제품, 강점, 차별점, 타겟 시장)로 정리
  3. 정리된 정형 데이터를 기반으로 LLM이 수출 타겟 ICP를 추론하고, 리드 소싱에 바로 쓰는 필터 조건으로 변환. 결제 후 하루 안에 소싱까지 이어지는 흐름으로 개편
Before

  • 기업 소개 필수
  • 제품 · 서비스 필수
  • 강점 · 차별점 필수
  • 영업 전략 필수
  • 타겟 산업 · 규모 필수
  • ICP 직접 작성 필수
  • 타겟 국가 · 직무 필수

  2. 파싱Crawl4AI · OCR 라이브러리
  3. 정형화LLM → 기업 정보 추출
  4. ICP 추론LLM → 수출 타겟 ICP
  5. 필터화소싱 필터 조건 자동 세팅

Result

03 / 05 — Scoring

LLM 기업 적합도 스코어링: 리드 품질 개선 및 리소스 비용 절감

Problem

필터 기반 1차 발굴만으로는 ICP에 맞지 않는 노이즈 기업이 항상 섞여 들어왔고, 그대로 리드가 전달되면 고객사 클레임으로 이어졌습니다.

Logic
  1. 1차 발굴 기업을 ICP와 함께 LLM에 전달해 적합도를 스코어링하고, 기준 미달 기업은 후속 단계에서 제외
  2. 통과 기업의 재직자 리스트에서 job title을 분석해 세일즈 타겟에 가장 가까운 핵심 리드 1인만 선정 (1기업 1리드 비즈니스 정책)
  3. 탈락 기업은 재직자 조회 · Enrichment를 호출하지 않아 외부 API 비용과 소싱 시간도 함께 감소
Funnel
  1. 1차 발굴 기업 필터 조건 기반 · 100%
  2. 2차 LLM 적합도 스코어링 ICP 적합도 점수 · 기준선 통과 85~90%
  3. 핵심 리드 1인 선정 기업별 재직자 중 job title 최적 1명

10~15% 부적합 사전 제외 산업·규모·타겟 시장·제품 연관성이 ICP와 어긋나는 기업을 리드 전달 전 단계에서 걸러냄

04 / 05 — Throughput

소싱 처리 속도와 처리량 개선

Problem

고객사 1개(300건) 소싱에 3~4시간이 걸렸고, 한 번에 1개 고객사만 처리할 수 있어 소싱 대기로 인한 딜레이가 누적되었습니다.

Logic
  1. 프롬프트 엔지니어링으로 품질을 끌어올려 낮은 reasoning effort에서도 같은 품질 확보, LLM 응답 시간 단축
  2. DAG max_active_runs=3으로 고객사 3개 동시 실행
  3. 외부 API rate limit에 맞춰 Airflow pool로 동시 호출 수 제어

05 / 05 — Cost

LLM 비용 최적화: 고객사당 리드 소싱 비용 월 $7~8에서 $1~1.5로 절감

Problem

고객사 수가 늘수록 LLM 토큰 비용과 외부 데이터 API 크레딧이 선형으로 증가했습니다. 같은 지침을 매 호출마다 다시 보내고, 이미 조회한 리드를 다시 과금하는 구조였습니다.

Logic
  1. 고정 지침·출력 스키마·예시는 시스템 프롬프트, 기업별 데이터만 유저 프롬프트로 분리해 prompt cache 적중 구간을 극대화
  2. 프롬프트 고도화로 품질을 확보한 뒤 reasoning effort를 하향. Effort를 하향해도 동일한 품질의 데이터 퀄리티 보장
  3. Enrichment 결과를 DB에 저장하고 재조회 시 캐시를 우선 사용해 외부 API 크레딧 재소모 방지 (테이블 설계 포함)
Prompt Structure

SYSTEM고정 · 매 호출 동일 CACHE HIT

  • 역할과 판단 기준
  • 출력 JSON 스키마
  • few-shot 예시

USER가변 · 기업별로만 바뀜

  • 고객사 ICP + 대상 기업 정보 (최소 토큰)

캐시 구간(시스템)이 토큰의 대부분을 차지하도록 설계해, 호출당 신규 과금 토큰을 유저 프롬프트 분량으로 축소

Cost Levers
  1. 프롬프트 구조화 + 캐싱 시스템/유저 분리로 prompt cache 적중률 극대화
  2. effort 하향 + 모델 교체 품질을 프롬프트로 확보한 뒤 reasoning effort 하향. 동일 퀄리티 결과 확보
  3. Enrichment DB 캐시 이미 조회한 리드는 외부 API 재호출 없이 DB에서 재사용
Result

$7~8 → $1~1.5

고객사 1개당 월 LLM 토큰 과금 절약

Enrichment 과금 절약
