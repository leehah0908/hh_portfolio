설계 결정

LLM 호출 대상을 SQL에서 먼저 줄인다

무엇을
3시간 주기로 변경분만 스캔하되, 활성 구독·온보딩 완료·내부 계정 제외 조건을 SQL EXISTS로 걸어 LLM에 도달하는 건수 자체를 최소화했습니다.
왜
LLM 비용과 지연은 호출 건수에 선형으로 붙습니다. 가장 싼 필터는 DB 안에 있습니다.
대안 대비
파이프라인 뒷단에서 걸러내는 방식은 이미 지불한 토큰을 버리게 됩니다.

자료를 이미지로 정규화해 멀티모달로 한 번에 읽힌다

무엇을
모든 형식을 LibreOffice로 PDF로 통일 → 페이지 PNG → 멀티모달 입력. 20MB·200페이지 가드를 둡니다.
왜
세일즈 자료는 표와 도식에 정보가 실려 있어, 레이아웃째로 봐야 의미가 유지됩니다.
대안 대비
텍스트 추출 방식은 표·도식이 많은 자료에서 정보를 잃어 채택하지 않았습니다.

자료 변경 여부로 재처리 범위를 나눈다

무엇을
프로필만 바뀐 경우 이미 정규화한 PDF를 재사용해 변환 단계를 생략하고, 자료가 바뀐 경우만 풀 리빌드합니다.
왜
변환은 CPU를, 재처리는 토큰을 씁니다. 바뀐 것만 다시 만드는 게 둘 다 아낍니다.
대안 대비
매 실행 전체 리빌드는 구현이 단순하지만 고객사 수에 비례해 비용이 증가합니다.

LLM에 맡길 것과 맡기지 않을 것을 갈라놓는다

무엇을
지역→국가(198개), 직무→키워드(104개) 전개는 결정론적 매핑으로 처리하고, LLM은 자료에서만 알 수 있는 키워드·산업·수출 유형만 추론합니다. LLM이 낸 산업 ID는 148개 사전과 교집합으로 검증해 위조 ID를 제거합니다.
왜
사전이 있는 문제를 LLM에 맡기면 검증 부담만 늘어납니다.
대안 대비
전개까지 LLM에 맡기면 출력 토큰이 커지고, 존재하지 않는 ID가 섞여 들어옵니다.

기존 고객사의 수동 튠 필터를 보존한다

무엇을
신규 고객사는 필터까지 생성하고, 기존 고객사는 필터 생성 단계를 self-skip하며 ICP 정의만 갱신합니다.
왜
운영 중 GTM팀이 손으로 다듬은 필터가 자동 생성으로 덮이면 리드 품질이 후퇴합니다.
대안 대비
DAG를 두 개로 분리하지 않고 Airflow trigger rule 하나로 두 경로를 표현해, 운영 대상이 늘지 않습니다.
04

프롬프트 구조

역할별로 분리한 4단계 프롬프트 체인. 각 단계는 한 가지 질문에만 답하고, 앞 단계의 출력이 다음 단계의 입력이 됩니다.

LLM에 맡긴 것 / 룰로 고정한 것

LLM에 맡긴 것 룰로 고정한 것
자료 이미지 → 마크다운 재구성 (사실만, 추론 금지, 도식은 “Figure:”로 서술) 지역 → 국가 198개 전개
바이어 산업·키워드 추론, 명시 ICP + 확장 ICP 직무 → 키워드 104개 전개
고객사 비즈니스 모델 분류 (4유형 + unknown) 산업 ID 화이트리스트 148개 교집합 검증
ICP 4축 키워드 리스트 (8~12개, 3~5단어) 규모 · 제외 국가 · 제외 직무 기본값

프롬프트 설계 원칙

공통 섹션 템플릿

모든 system prompt가 [Role] · [Context] · [Task] · [Input] · [Guidelines/Rules] · [Priority] · [Output] 순서로 통일되어 있습니다. 수정과 리뷰가 쉽습니다.

두 주체 분리

“고객사(판매자)”와 “바이어(구매자)”를 혼동하지 않도록 별도 섹션으로 명시합니다. 산업·키워드는 바이어 기준, export_type은 고객사 기준입니다.

export_type을 체인 전체의 렌즈로

2단계에서 분류한 고객사 비즈니스 모델(브랜드 수출 / OEM·ODM / 기술 서비스 / 복합)이 3·4단계 프롬프트에 주입되어 “누가 바이어인가”의 방향을 결정합니다. 기업 판별은 유형별 system prompt 4개로 분기합니다.

출력 계약을 좁게

JSON만 허용하고, 필드·항목 수·단어 길이·용어 수준(카테고리 수준, 브랜드명 금지, 직무는 기능만·직급 금지)까지 명시합니다. 코드에서 파싱 후 사전 검증을 거칩니다.

내부 추론, 외부 출력 최소

“생각은 내부에서, 출력하지 말 것” 지시와 함께 대량 판정은 reasoning 없이 실행해 출력 토큰과 지연을 줄입니다. system은 정적, user는 가변으로 나눠 prefix cache 적중을 유도합니다.

프롬프트 원문은 S3에 외부화되어 코드 배포 없이 개정합니다. 이 페이지에는 구조와 원칙만 담았습니다.

Apollo 기업·컨택 응답을 컬럼 1:1로 PostgreSQL에 저장합니다. 벌크 조회 1회로 페이지 전체의 히트를 판정하고, 동시 실행에 대비해 ON CONFLICT DO NOTHING을 씁니다.
왜
히트와 미스의 하류 코드 경로가 동일해져, 캐시가 있다는 사실이 로직에 새지 않습니다.
대안 대비
정규화한 스키마로 저장하면 매핑 코드가 두 벌 생기고 API 변경에 취약해집니다.

중복 소싱을 API 호출 전에 막는다

무엇을
이전 run의 검수 이력(S3)을 모두 대조해, 이미 본 기업은 검색 결과 단계에서 스킵합니다.
왜
중복은 크레딧과 신뢰를 동시에 깎습니다. 업로드 중복 0건을 유지하고 있습니다.
대안 대비
업로드 직전 dedupe는 이미 지불한 enrich 크레딧을 회수할 수 없습니다.

부분 성공을 버리지 않는다

무엇을
429는 지수 백오프 5회 후 sentinel로 중단하되, 그때까지 확보한 분량은 저장합니다. 탐색 상한에 도달하면 “수율 저조, 필터 재설정 필요” 경보를 냅니다.
왜
외부 API 한도는 통제 밖입니다. run 전체를 실패로 처리하면 그날의 결과물이 0이 됩니다.
대안 대비
전량 성공만 커밋하는 방식은 재실행 비용이 그대로 다시 듭니다.

비용을 run 단위로 계측한다

무엇을
토큰(캐시 적중분 분리)과 API 크레딧을 task 간 XCom으로 누적해, run 종료 시 단일 리포트로 남깁니다.
왜
측정하지 않으면 프롬프트 수정이 비용에 어떤 영향을 줬는지 말할 수 없습니다.
대안 대비
대량 반복 판정은 reasoning 없이, 저빈도 고난도만 medium으로 — 워크로드별 분리는 이 계측이 있어서 판단할 수 있었습니다.
04

프롬프트 구조

판별은 보수적으로, 선택은 우선순위로.

1차 기업 판별 = 노이즈 필터

“정밀 매칭이 아니라 명백한 오분류만 걸러낸다”를 프롬프트가 스스로 선언합니다. 하드 제외(경쟁사)는 보수적으로, 나머지는 “연결 가능성이 조금이라도 있으면 eligible”. recall 우선을 명시해 리드 수율을 지킵니다.

수출 유형별로 “누가 경쟁사이고 누가 바이어인가”의 정의가 달라, system prompt 4개로 분기합니다.

2차 담당자 선택 = 우선순위 체인

contact_fit·target_jobtitles 매치 → 도메인 관련성 → 직급(target_seniorities) → 임원 fallback 순서를 번호로 고정합니다. 제외 직무(assistant·intern 등)를 명시합니다.

출력은 “목록에 있는 id를 그대로 복사”만 허용합니다.

출력 계약

단계 출력
1차 기업 판별 {"eligible": "eligible" | "ineligible"} — JSON 한 필드
2차 담당자 선택 raw id 문자열 하나

파싱 실패는 None으로 스킵하고, 실행 전체를 멈추지 않습니다.

07

배운 점과 한계

배운 점 — 캐시는 스키마를 바꾸지 않을 때 가장 싸다

API 응답 shape을 그대로 저장한 덕분에 히트/미스 분기가 조회 함수 안에서 끝났습니다. 캐시를 붙이면서 하류 로직을 한 줄도 고치지 않았고, 이후 응답 필드가 늘어날 때도 컬럼 추가로 흡수했습니다.

한계 — 2차 선택 출력에 사전 검증이 없다

2차 담당자 선택의 LLM 출력(id)을 후보 목록과 대조하는 코드 검증이 없습니다. hallucination이 발생하면 예외 없이 조용히 유실됩니다. 1차 판별과 같은 사전 검증 패턴을 적용할 예정입니다.
